# 데이터 요구사항 및 개념 모델링

## 1. 개요

- **목적:** PlanPing의 요구사항을 바탕으로 필요한 데이터를 도출하고 개념적 데이터 모델링을 정의한다.
- **작성일:** 2026.10.30

## 2. 주요 기능과 도메인 요구사항

* 회원
    * 사용자는 이메일과 비밀번호로 회원가입, 로그인할 수 있다.
    * 사용자는 회원 정보를 수정할 수 있다.
    * 사용자는 회원 탈퇴할 수 있고, 탈퇴 시 정보가 삭제된다.

* 계획
    * 사용자는 계획의 카테고리(루틴/일일)를 지정해 계획을 생성할 수 있다.
    * 사용자는 본인이 작성한 계획을 조회할 수 있다.
    * 사용자는 계획을 수정/삭제할 수 있다.
    * 사용자는 계획을 완료 상태로 변경할 수 있다.
    * 사용자는 일간/주간 통계를 확인할 수 있다.
    * 계획 완료 이후 계획에 대한 회고를 작성할 수 있다.
    * 계획에 대한 상세 계획을 추가할 수 있다.(ex: 알고리즘 문제 풀이 -> 프로그래머스 문제 풀이(0/3))


* 알림
    * 알람 설정이 된 계획의 경우 시간이 되면 사용자에게 알람을 발송한다. 



## 3. 엔티티 도출

| 엔티티명 | 설명 | 주요 속성 |
|:--- | :--- | :--- |
| Users | 시스템을 사용하는 회원 정보 | 아이디, 비밀번호, 전화번호, 이메일, 가입일, 수정일 |
| Roles | 권한 정보 | 권한 명, 권한 설명 |
| RoutinePlans | 요일별로 반보되는 기본 계획표 | 사용자 키, 요일 |
| RoutinePlansItems | 기본 계획표의 시간별 세부 항복 | 루틴 계획 키,시작 시간, 종료 시간, 계획 내용, 알람 여부 |
| DailyPlans | 특정 날짜에 확정된 실제 일일 계획 | 사용자 키, 날짜  |
| DailyPlansItems | 특정 날자의 시간별 실제 수행/변경 계획 | 일일 계획 키, 시작 시간, 종료 시간, 계획 내용, 알람 여부, 완료 여부, 회고 |
| DailyPlansItemsDetail | 수행 계획의 상세 내용 | 수행 계획 키, 상세 내용, 목표 횟수, 수행 횟수 |
| Alarms | 사용자에게 발송한 알람 | 알람 내용, 보낸 시간, 확인 여부, 계획 키 |


## 4. 비즈니스 규칙 및 관계 

* **Users - Roles(1:1)**
    * 한 명의 사용자는 한 개의 권한을 가진다.
    * 상위 권한은 하위 권한을 포함한다.
    * 사용자가 탈퇴하는 경우 권한은 삭제된다.
* **Users - RoutinePlans(1:n)**
    * 한 명의 사용자는 요일별로 한 개씩 가질 수 있다.
    * 사용자가 탈퇴하는 경우 플랜은 삭제된다.
* **Users - DailyPlans(1:n)**
    * 사용자는 여러개의 일일 계획을 가질 수 있다.
    * 하나의 날짜에는 하나의 계획만이 들어갈 수 있다. (날짜 속성 유니크 제약)
* **Users - Alarms(1:n)**
    * 사용자는 여러개의 알람을 가질 수 있다.

* **RoutinePlans - RoutinePlansItems(1:n)**
    * 루팅 계획은 여러개의 플랜 아이템을 가질 수 있다.
        * (요일별, 같은 요일 다른 시간대 등)
        * Items는 동일 요일에서 겹치는 시간을 설정할 수 없다.
* **DailyPlans - DailyPlansItems**
    * 루팅 계획은 여러개의 플랜 아이템을 가질 수 있다.
        * (요일별, 같은 요일 다른 시간대 등)
        * Item은 다른 item과 겹치는 시간을 설정할 수 없다.
* **DailyPlansItems - DailyPlansItemsDetail**
    * 하나의 아이템은 여러 개의 상세계획을 가질 수 있다.
        * 없어도 된다.



## 5. 가정 및 제약 사항
* **루틴 계획 복사(Snapshot):** 사용자가 특정 날짜의 계획을 처음 조회할 때, 해당 요일의 `RoutinePlans` 하위 데이터를 `DailyPlans` 데이터로 복사하여 생성한다.
* **시간 겹침 방지:** 어플리케이션(Spring Boot) 비즈니스 로직 단에서 시간 범위(Start Time ~ End Time)의 교집합을 검증하여 겹치는 일정이 등록되지 않도록 방어한다.
* **데이터 삭제 정책:**
    * `Users`, `RoutinePlans`, `DailyPlans`: 통계 유지 및 실수 복구를 위해 **Soft Delete (논리적 삭제)**를 기본으로 한다.
    * `ItemDetails`, `Alarms`: 데이터가 쌓이는 속도가 빠르고 굳이 보관할 필요성이 적으므로 **Hard Delete (물리적 삭제)**를 적용한다.
* **데이터 보호:** 비밀번호와 개인정보같은 정보는 암호화 진행 후 저장한다.(이름, 전화번호, 이메일, 등)
